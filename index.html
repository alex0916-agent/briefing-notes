1. 한눈에 결론
결론

기존 주소의 404는 HTML 코드나 카카오 캐시 문제가 아니라, 기존 계정 alex750916과 저장소 alex-readable-docs가 현재 GitHub API에서 접근되지 않기 때문에 발생합니다.

01기존 호스트 소실

기존 계정·저장소가 현재 API에서 404로 응답됩니다.

02신규 Pages는 진행 중

신규 저장소는 Pages가 생성됐지만 상태가 아직 building입니다.

03커버 구성도 미복제

현재 테스트 저장소에는 cover.jpg와 og:image가 없습니다.

5. 원인 구조
기존 계정 정지·접근 불가→기존 저장소 API 404→기존 Pages 호스트 404
신규 저장소 생성→Pages building→HTTP 200 전 최종 확인 필요

원인 A · 기존 주소가 살아 있지 않음

현재 API에서 alex750916 사용자와 alex-readable-docs 저장소가 모두 404입니다. 따라서 기존 URL은 원본 HTML을 다시 찾을 수 있는 주소가 아니라, 접근 불가능한 이전 호스트가 되었습니다.

원인 B · 현재 테스트는 Pages 완료 전 상태

신규 저장소의 Pages 객체는 생성되었지만, Actions 실행이 아직 building입니다. 설정 생성과 실제 공개 완료를 혼동하면 “배포됐는데 404”처럼 보일 수 있습니다.

원인 C · 카카오 커버 재현 구성 누락

현재 저장소에는 커버 이미지와 og:image 메타데이터가 없으므로, Pages가 성공해도 과거처럼 카카오톡에 커버 이미지가 표시되지 않습니다.

7. 재발 방지 기준
  • 배포 전 계정, 저장소, 기본 브랜치, Pages source를 먼저 확인한다.
  • Actions가 Success가 되기 전에는 “배포 완료”로 보고하지 않는다.
  • 최종 URL을 직접 열어 HTTP 200과 실제 본문을 확인한다.
  • 카카오 공유가 목적이면 cover.jpg, og:image, og:image:secure_url를 공개 파일 allowlist에 포함한다.
  • 계정 변경 시 기존 URL과 신규 URL을 별도 관리하고, 이전 URL의 생존을 전제로 하지 않는다.
  • 임시 검수 저장소와 최종 공개 저장소를 분리하고, 폐기 시점과 보존할 배포 이력을 함께 기록한다.

8. 현재 판단
현 단계 판정

GitHub 연결 및 Pages 설정 생성은 성공했지만, 과거의 완성형 공개 배포와 카카오톡 커버 미리보기까지 복구된 상태는 아닙니다.

따라서 다음 단계는 신규 계정의 별도 공개 저장소에 검수용 번들을 다시 구성하고, Pages Success·HTTP 200·Open Graph 커버 응답을 순서대로 확인하는 작업입니다. 이 보고서 작성에서는 추가 재배포나 저장소 변경을 수행하지 않았습니다.
