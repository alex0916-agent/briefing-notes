한눈에 결론

구현 설계 v1.0 · 공급사 계약 확인 후 개발 착수

기존 장치 포맷은 어댑터에서 수용하고, Haps 내부 데이터는 언어·제조사에 독립적인 계약으로 정규화한다. 운영 투입은 아직 NOT_READY이며 이 문서는 구현 완료 보고가 아니다.

  • 실제 수집 경로가 먼저다. 코드 감사에서 MQTT 수집기의 운영 연결은 확인되지 않았다. 응답 프롬프트 변경만으로 실시간 관제를 구현할 수 없다.
  • 저장 책임을 명확히 한다. 브로커 수신 확인과 DB 저장 완료는 다른 단계다. 중복 제거·영속 저장·재전송을 하나의 계약으로 검증한다.
  • 신뢰도와 최신성을 분리한다. 통신 상태, 센서 오류, 측정 시각, 과거 재전송을 각각 기록해야 안전한 판정이 가능하다.
  • 첫 PoC는 읽기 전용이다. 제조설비 제어·원격 설정 변경·법적 인증 취소 자동판정은 범위 밖이다.

결정 필요: PoC 사업장·장치 1종, 보안 접속 방식, 저장 책임과 펌웨어 기능 상태, 데이터 보존·권한 범위.

즉시 영향: 제품 코드·DB·센서 설정은 변경하지 않는다. 개발 일정과 비용은 전체 payload·장치 수·보존기간 확인 후 산정한다.

다음 행동: AlexLAB 기술 담당과 올젠케어가 미제공 통신 문서·전체 메시지·현재 펌웨어를 확인하고 G0 계약 게이트를 공동 종료한다. 아래 담당은 제안 역할이며 실제 배정은 미확정이다.

공개용 기술 설계. 계정·암호·내부 호스트·장치 식별값·비밀 알고리즘 상수·보안 재현 절차는 포함하지 않는다. 이번 승인 범위는 문서 작성·공개이며 실제 개발·장치 연결 승인은 별도다.

위 명칭은 구현 책임을 나눈 설계 이름이다. 기존 파일·클래스·테이블이 이미 존재한다는 뜻이 아니다. 정확한 코드 배치는 개발 승인 후 기존 모듈 경계를 확인해 확정한다.

연결·인증·Tenant 격리
  • 전송 보호: TLS와 서버 인증서·hostname 검증을 기본으로 한다. 장치가 지원하지 않으면 승인된 현장 보안 게이트웨이/터널과 네트워크 경계를 검토한다. 포트 번호만으로 보안을 판정하지 않는다.
  • 권한 분리: 장치는 허용 토픽 발행, collector는 허용 토픽 구독만 가능하게 한다. 장치 clientId와 collector clientId는 분리한다.
  • 장치 신원: 사용자명·인증서·토픽 ACL과 registry가 연결되어야 한다. payload의 MAC/tenant 값만 신뢰하지 않는다.
  • 공통 토픽 주의: 표준 MQTT 구독 메시지만으로 원 발행자의 인증 계정을 알 수 있다고 가정하지 않는다. 장치별 ACL 토픽, broker가 검증한 identity 전달 또는 서명된 envelope 중 합의된 경로가 필요하다.
  • 보관 보호: raw payload·인증정보 접근을 분리하고 secret manager/OS 보호 저장소·키 회전·백업 접근권한을 검증한다. 로그에는 비밀값을 남기지 않는다.
  • 조회 격리: session 기반 tenant/plant/role 검증을 조회 전에 적용한다. 서비스 계정이 RLS를 우회할 수 있으면 repository 계층에서도 범위를 강제하고 교차 tenant 시험을 수행한다.

서버 수신 후 해시/HMAC는 수신 이후 변경 검증에 쓰인다. 센서 자체의 오류, 상류 사칭 또는 인증되지 않은 발신을 해결하는 기능은 아니다.

업체 제공 인증 검증값은 독립된 보안 경계로 검증한다. 본 공개본에는 비공개 계산식·상수·공격 재현 입력을 싣지 않는다. TLS·인증·ACL의 역할 구분은 Mosquitto 공식 설정 문서를 참고하되 실제 업체 broker 제품·설정을 가정하지 않는다.

Canonical 데이터 계약

신규 제안 계약이며 실제 공급사 payload가 아니다. 원문은 보존하고 어댑터가 변환한다. 아래 ID·시각·수치는 모두 합성 예시다.

{
  "schema_version": "haps.telemetry.v1",
  "event_id": "evt-demo-001",
  "registry_version": "demo-v1",
  "tenant_id": "tenant-demo",
  "plant_id": "plant-demo",
  "line_id": "line-demo",
  "asset_id": "asset-demo",
  "device_id": "device-demo",
  "channel_id": "temperature-1",
  "metric": "temperature",
  "value": 4.2,
  "unit": "Cel",
  "quality": "GOOD",
  "quality_reasons": [],
  "occurred_at": "2026-09-16T00:00:00Z",
  "received_at": "2026-09-16T00:00:02Z",
  "time_valid": true,
  "source_message_id": null,
  "boot_id": null,
  "sequence": null,
  "replay": "UNKNOWN",
  "identity_assurance": "VERIFIED",
  "raw_ref": "raw-demo-001",
  "payload_sha256": "<server-computed>",
  "adapter_version": "vendor.v1"
}
필드군강제할 계약
ID / Registrytenant·plant·asset는 서버 registry에서 결정. 매핑 변경 이력을 버전으로 보존하며 과거 재전송은 발생 시점에 유효한 매핑을 사용. 불명확하면 격리
시각UTC occurred_at와 received_at 분리. 시각 무효이면 occurred_at=null, 원래 값은 raw에 남김. 초/ms 자동 추측 금지
품질GOOD / UNCERTAIN / BAD. 오류 사유는 별도 canonical code. 연결 OFFLINE·최신성 STALE은 측정 품질과 별개
숫자 / 단위NaN·Infinity·비정상 범위를 거절. 오류 sentinel은 value=null + BAD로 변환. 단위 변환과 원단위·변환 버전 추적
식별 / 재전송없던 message_id·boot_id·sequence를 만들어 장치 원본 값처럼 표시하지 않음. 서버 event_id와 장치 ID 구분. replay=LIVE/BACKFILL/UNKNOWN
버전 / 참조schema·adapter·registry·rule version 및 raw hash를 연결. 스키마 미지원은 조용히 수용하지 않음

한 메시지에 여러 채널이 있으면 envelope 하나와 channel observation 여러 개로 분리한다. 배열 순서만으로 영구 채널 ID를 정하지 않고 공급사 채널 정의를 고정한다. 이식 가능한 단위 코드는 내부 계약으로 확정하고 UI에서 현지 표기를 적용한다.

저장 모델·멱등성·트랜잭션

아래는 논리 모델 제안이며 migration 실행 결과가 아니다. 초기에는 관계형 DB와 transactional outbox를 사용하고 time-series 확장은 조회·보존 요구를 측정한 뒤 선택한다.

논리 엔터티주요 데이터 / 제약
device_registry + assignment_historydevice identity, tenant/plant/asset, valid_from/to, enabled, credential_ref. 설치·교체 이력 보존
raw_ingest / delivery_receipt수신 원문 참조·hash·received_at·broker/profile·validation 결과. 비밀 필드 노출 제한·원문 접근 감사
message_identityregistry device + source ID 또는 legacy 시각 키 + identity policy version. unique 제약과 정규 payload hash
observationsevent_id/channel_id/metric, value/unit/quality, occurred_at/received_at, source_ref. envelope와 측정 중복을 구분
device_status / current_state마지막 접속 관측·유효 측정·품질·최신성·신뢰 수준. 무조건 last-write-wins 금지

멱등 처리 규칙

  1. 가능하면 source message_id 또는 device + boot_id + sequence를 사용한다. MQTT Packet Identifier를 업무 키로 쓰지 않는다.
  2. 기존 device + timestamp 방식은 조건부 legacy 계약으로만 수용한다. 동일 키·동일 의미 payload는 중복, 동일 키·다른 내용은 CONFLICT로 보존한다.
  3. raw bytes hash와 의미 payload hash를 구분한다. JSON 순서·재전송 표식처럼 transport-only 필드를 제외할지는 버전 있는 계약으로 확정하며 측정값은 제외하지 않는다.
  4. DB unique 제약과 transaction으로 경쟁 요청을 직렬화한다. 애플리케이션의 사전 SELECT만으로 중복을 막지 않는다.
  5. status에 source ID가 없으면 “완전한 이벤트 중복 제거”를 약속하지 않는다. 수신 기록은 보존하고 알림은 상태 전이·incident lifecycle 기준으로 멱등 처리한다.

ACK·재시도·장애 복구

장치 → broker PUBACK ≠ Haps DB commit. consumer ACK를 늦춰도 장치에 DB 저장 사실이 자동 전달되지는 않는다. OASIS MQTT §4.3

선택지장점한계 / 도입 조건
A. Broker 내구성 + durable inbox장치 포맷 변경 최소화. 초기 후보broker persistence·세션·큐 한도·consumer commit 후 ACK·백업 장애 범위를 검증해야 함
B. DB 기반 application ACK장치가 저장 완료까지 보관 가능펌웨어 변경, ACK 토픽/권한·correlation·재시도·영속 outbox 계약 필요
C. 보호된 현장 relay + 영속 spool레거시 장치와 서버 분리, 현장 장애 흡수추가 장비·운영·디스크·보안 책임. 장치→relay 구간 공백은 별도

권장: A의 내구성이 검증되면 읽기 전용 PoC에 채택한다. 요구 RPO를 만족하지 못하면 B 또는 C를 별도 승인한다. “무손실”이라는 표현은 합의된 장애 범위·저장 한도 시험 전 사용하지 않는다.

→ bounded parse + identity/schema checks
→ COMMITTED_INBOX 또는 COMMITTED_QUARANTINE
→ consumer ACK
→ normalize + observations + outbox transaction
→ idempotent projection / rule evaluation
→ PROCESSED

DB 미저장 → ACK 성공 처리 금지 → bounded backpressure / reconnect
일시 장애 → backoff + jitter + 제한된 재시도
영구 형식 오류 → 접근 제한 quarantine + 운영 알림
같은 업무 키·다른 내용 → CONFLICT (덮어쓰기 금지)

악성·과대 payload는 저장 상한 내에서 요약·hash·거절 사유만 보존하도록 별도 보안 정책을 둔다. 무한 재전송·무제한 quarantine도 허용하지 않는다. 중복 재수신 후 crash가 발생해도 규칙·Incident가 중복 생성되지 않아야 한다.

Paho 사용을 선택한다면 ACK 제어·세션 보관·재구독을 설치 버전에 맞게 시험해야 한다. 공식 Client API는 구현 근거이며 패키지 설치 승인이 아니다.

NTP 동기화만으로 시각의 고유성·단조 증가를 보증할 수 없다. RFC 5905의 시계 조정과 별개로 메시지 식별·순서 계약이 필요하다.

제출 사양의 부팅 후 시각 확보 전 미저장 구간은 복구 가능한 backlog가 아니라 결측이다. 배터리 RTC·상대시각 저장/사후 매핑·운영 제약 중 공급사가 지원할 방식을 확인한다. 확인되지 않은 값을 보간해 실측으로 표시하지 않는다.

과거 위험 이벤트는 별도 historical Incident로 검토할 수 있지만 현재 경보를 자동 재발령하지 않는다. 같은 시각/다른 sequence의 우선순위와 허용 지연은 metric별 정책으로 버전 관리한다.

실시간 상태·Themis·Aegis·Haps 연결

상태는 하나의 “정상/비정상” 값으로 압축하지 않는다.

상태 축제안 값판단 증거
수집기CONNECTED / DEGRADED / DISCONNECTEDcollector 연결·구독 승인·DB 적재 health
장치 연결 관측ONLINE / OFFLINE / UNKNOWN인증된 heartbeat/LWT/실제 수신. collector 연결과 별개
측정 최신성FRESH / STALE / UNKNOWN마지막 유효 occurred_at, 기대 주기, 허용 지연
측정 품질GOOD / UNCERTAIN / BAD센서 오류·교정·값 범위·시각 신뢰
보호 기능ACTIVE / INACTIVE / UNKNOWN펌웨어 버전과 실제 상태 증거. 미연결만으로 buffer ACTIVE 추정 금지

ThemisAX: locale-independent event와 승인된 rule_version을 사용한다. 장치/시간/품질/적용 범위가 충족되지 않으면 INSUFFICIENT_DATA를 반환한다. 온도 기준 등 법정·공정 수치를 임의 하드코딩하지 않는다.

AegisAX: raw hash → 정규 event → rule version → decision → 사용자 조회를 연결한다. 무결성 기록은 장치 교정이나 법적 적합성 인증이 아니며, 로컬 파일만으로 immutable storage를 주장하지 않는다.

Haps: 상태 질의는 허용된 Telemetry Read Tool로 처리한다. 최신 snapshot과 evidence handle을 먼저 확인하고, 규정 설명이 필요할 때만 별도 RAG를 결합한다. 법령 문서와 현장 측정 근거를 구분한다.

“현재 상태 → 확인 시각·장치 범위 → 근거 핸들 → 필요한 조치”로 답변하며 실제 수집이 없으면 미연동/미확인을 표시한다. ko/en/vi 표현이 달라도 Event·Decision Code는 동일하다.

조회 API·Tool 계약·권한

다음 endpoint와 tool은 제안이다. 기존 API를 변경하거나 새 route를 배포하지 않았다.

제안 계약용도필수 제한

tenant는 모델이 임의 지정하는 값이 아니라 인증 session에서 결정한다. Tool 결과에는 snapshot_id, observed_at, received_at, stale, quality, decision_code, evidence_refs를 포함한다. 사용자 설명 문자열은 canonical code와 분리해 localize한다.

read-only 계정으로 PLC/MES write, 장치 재부팅, 설정 변경, 키 회전, firmware update를 실행하지 않는다. 향후 쓰기는 Policy Validation → Human Approval → Safety Validation → 전용 connector 및 감사 구조가 선행되어야 한다.

제출 문서의 120초 주기·최대 7일·500ms 재전송 간격을 이용한 계산값이다. 실측 성능이나 SLA가 아니다.

전환과 복구

  1. 별도 테스트 broker/합성 fixture → 승인된 실장치 1종 → 제한된 Pilot 순서로 확대한다.
  2. feature flag와 전용 subscriber를 사용하며 기존 수집기가 있다면 동일 clientId 재사용으로 중단시키지 않는다.
  3. 실패 시 신규 collector를 중지하고 flag를 해제한다. 장치 outbox·원본 기록·기존 DB를 삭제하거나 초기화하지 않는다.
  4. DB 변경은 additive migration·backup/restore 검증·권한 회귀 후 별도 승인한다. schema rollback보다 읽기 경로 분리를 우선 검토한다.
